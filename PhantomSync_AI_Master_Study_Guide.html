1. The Mental Model: How to Build a Full-Stack Project from Scratch

When you start with an empty folder, building a complete project can feel overwhelming. Professional Software Engineers follow a structured, phased mental model that removes all guesswork:

PHASE 1: Requirements & Data Design ──► Define the problem, schemas (Note, History, Queue). │ ▼ PHASE 2: Backend Core & Database ──► Connect DB, build REST endpoints, test with Postman/cURL. │ ▼ PHASE 3: Automated Test Verification──► Write tests to prove edge cases work BEFORE UI is built. │ ▼ PHASE 4: Frontend Data Layer ──► Set up IndexedDB & SyncManager before building UI components. │ ▼ PHASE 5: UI & Interactive Features ──► Build Navbar, Editor, Conflict Modals, and visual diffs. │ ▼ PHASE 6: Hardening & Resilience ──► Network simulation, exponential backoffs, idempotency.
Key Rule of Engineering
Never write frontend UI code before your data layer works. In PhantomSync, we first designed the data models and verified sync mechanics through 16 automated tests before writing a single line of React UI!

2. High-Level Architecture & Component Map

PhantomSync AI solves the fundamental problem of web applications: network unreliability. In a traditional app, if the Wi-Fi disconnects, the user cannot write or save notes. In PhantomSync:

  • IndexedDB is the primary source of truth for the browser. When the user types or creates a note, it writes directly to browser disk with 0ms delay.
  • The Network is an asynchronous replication channel. A background coordinator (SyncManager) pushes changes to the cloud when online and pulls updates from other devices.

3. The Database Connection: Real MongoDB vs In-Memory Fallback

One of the biggest frustrations for beginners on Windows is setting up local databases (e.g. MongoDB service not starting, environment variable PATH errors).

In PhantomSync, we engineered a Dual-Mode Database Connector in server/src/config/db.js that guarantees 100% uptime with zero manual setup.

How the Dual-Mode Connection Logic Works

// File: server/src/config/db.js
const mongoose = require('mongoose');
const memoryStore = require('./memoryStore');

async function connectDB() {
  const uri = process.env.MONGODB_URI || 'mongodb://localhost:27017/phantomsync';

  try {
    // 1. Attempt connection to real MongoDB with a 2-second timeout
    const conn = await mongoose.connect(uri, { serverSelectionTimeoutMS: 2000 });
    console.log(`[Database] Connected to external MongoDB at: ${conn.connection.host}`);
    memoryStore.isInMemory = false;
    return conn;
  } catch (err) {
    // 2. If real MongoDB is not running, gracefully switch to built-in in-memory store!
    console.warn(`[Database] External MongoDB not reachable (${err.message}).`);
    console.log(`[Database] Switching to built-in high-performance in-memory store!`);
    memoryStore.isInMemory = true;
    return { connection: { host: 'in-memory-store' } };
  }
}
Why This Impresses SDE Interviewers
This is an implementation of the Adapter and Fallback Pattern. The rest of the server code (controllers, routes, tests) does not care whether the database is real MongoDB or in-memory; they share the exact same Mongoose API (find, findById, create, save).

The browser uses 3 distinct IndexedDB stores initialized in client/src/db/indexedDb.js:

  • notes: Stores all notes locally on browser disk. Keys are note _ids.
  • syncQueue: The Transactional Outbox. Contains mutations (create, update, delete) waiting to be pushed to the server.
  • metadata: Stores local client configuration, persistent clientId, and the lastSyncedAt timestamp.

6. Optimistic Concurrency Control (OCC) & Conflict Detection

Why Not Last-Write-Wins (LWW)?

Most simple applications use Last-Write-Wins where whoever sent the last timestamp overwrites previous changes. In professional engineering, this is considered a critical anti-pattern:

  • Clock Drift: Laptop and phone clocks drift by seconds or minutes. A device with a fast clock will permanently destroy edits from devices with accurate clocks.
  • Silent Data Loss: If Developer A writes a bug fix offline and Developer B rewrites the function online, LWW silently erases Developer A's fix without anyone knowing!

PhantomSync's Solution: Optimistic Concurrency Control (OCC)

// In noteController.js & syncController.js:
if (baseVersion !== undefined && !isConflictResolution) {
  if (existingNote.version !== Number(baseVersion)) {
    // CONFLICT DETECTED!
    // Server is at v2, but client edited from v1.
    // NEVER overwrite! Preserve both versions and return HTTP 409 Conflict.
    return res.status(409).json({
      error: 'ConflictDetected',
      serverNote: existingNote,
      attemptedUpdate: { title, content, tags, baseVersion }
    });
  }
}
The Invariant
PhantomSync guarantees that no committed edit is ever silently overwritten. The server returns both the remote version and the attempted local version, giving full agency to the user.

7. Side-by-Side Visual Diff & Built-in 3-Way AI Merge

When a conflict occurs, PhantomSync pops up the ConflictResolverModal. It features:

A. Color-Coded Line Diff Highlighter

We built client/src/services/diffHelper.js to calculate line-by-line divergences:

  • Red / Amber (•): Lines unique to the local offline version that differ from server.
  • Green (+): Lines added or updated on the remote server.
  • Standard Text: Common ancestor lines that both parties agree on.

B. The 3-Way Merge Algorithm (Works with Zero API Keys!)

Implemented in server/src/services/aiMergeService.js. It compares 3 distinct documents:

  1. Base ($V_0$): The common ancestor note before the split occurred.
  2. Server ($V_1$): What was saved to the server by another session.
  3. Local ($V_1'$): What was edited offline on the user's client.
// Example reconciliation rule in threeWayLineMerge:
if (remoteLine === baseLine && localLine !== baseLine) {
  // Only local modified this line -> safely adopt local change!
  resultLines.push(localLine);
} else if (localLine === baseLine && remoteLine !== baseLine) {
  // Only remote modified this line -> safely adopt remote change!
  resultLines.push(remoteLine);
} else if (localLine !== remoteLine) {
  // Both parties modified the line -> non-destructively synthesize both!
  resultLines.push(localLine);
  resultLines.push(remoteLine);
}

8. Time Travel Version History & Point-in-Time Restore

Every time a note is created, updated, or conflict-resolved, an immutable snapshot is saved to NoteHistory.

When a user clicks "Restore Version 1":

  1. The server finds the snapshot for revision 1 in NoteHistory.
  2. It updates the live note with revision 1's title and content.
  3. It increments the version to revision 4 (supposing current was 3).
  4. It records a new snapshot with changeType: 'restore' and summary: 'Restored from version 1'.

Important SDE interview concept: Restores do not delete intermediate history! The timeline remains purely append-only, preserving complete auditability.

10. Top 10 SDE Placement Interview Questions & Model Answers

Q1: Why did you choose IndexedDB instead of LocalStorage for offline storage?

Answer: localStorage is synchronous and blocks the main UI thread during large reads or writes. Furthermore, it is capped at only 5MB and only stores strings. IndexedDB is asynchronous, operates in the background without UI lag, supports large binary/structured data (hundreds of MBs), offers ACID transactions, and allows creating indexes for fast queries.

Q2: What is the Transactional Outbox pattern and why did you use it?

Answer: When a user performs an offline edit, writing directly to the network might fail. With the Transactional Outbox pattern, we save the note to the local notes table and atomically enqueue a mutation task into syncQueue. A separate worker (SyncManager) drains this queue when online. If the app crashes or network fails, the queue is persisted on disk and never lost.

Q3: How do you prevent duplicate requests when retrying sync over an unstable network?

Answer: Through Idempotency Keys. Every queued mutation is tagged with a client-generated UUID idempotencyKey. When the server processes an operation, it records the key and the resulting response in the SyncLog collection. If the connection dropped before the client received the 200 OK and retries, the server recognizes the key and returns the cached result without repeating the mutation.

Q4: What is the difference between Optimistic Concurrency Control (OCC) and Pessimistic Locking?

Answer: Pessimistic locking locks the database record as soon as a user opens it for editing, preventing anyone else from editing until released. In mobile and web apps, pessimistic locking is unviable because users go offline or close tabs without unlocking. OCC assumes conflicts are rare: it lets anyone edit freely and checks the document version at write time. If the base version is stale, it flags a conflict.

Q5: Why did you use soft deletes (Tombstones) instead of hard deleting documents?

Answer: In distributed offline-first systems, hard deleting a row removes all trace of it. If Client A deletes Note 1 offline, and Client B comes online later, how does Client B know Note 1 was deleted rather than never existing? With a Tombstone (isDeleted: true with incremented version), the deletion is a trackable event that synchronizes cleanly across all distributed clients.

Q6: How does your AI merge suggestion work when the user has no Gemini or OpenAI API key?

Answer: PhantomSync includes a built-in deterministic 3-way text reconciliation algorithm. It compares the common ancestor (Base) against the Server and Local versions line-by-line. Non-overlapping edits are united cleanly without loss. If an API key is provided, it can escalate to Google Gemini LLM for semantic synthesis, but the app is 100% functional out of the box with zero external dependencies.

Q7: What happens when the server goes down while the client is syncing?

Answer: The client triggers an Exponential Backoff retry algorithm with jitter. Instead of spamming the failed server every second, the client waits $2\text{s}, 4\text{s}, 8\text{s}, 16\text{s}$, up to a $30\text{s}$ cap. The operations remain safely queued in IndexedDB until connectivity returns.

Q8: Why are note IDs generated as UUID strings on the client rather than auto-incremented integers on the server?

Answer: If IDs were auto-incremented integers generated by MongoDB/Postgres, an offline user creating 5 notes would not have IDs for them until they reconnect, breaking local relations and foreign keys. UUIDv4 provides 128 bits of entropy ($3.4 \times 10^{38}$ possible IDs), making collisions mathematically impossible even across millions of independent offline devices.

Q9: How do you ensure test isolation in automated integration testing?

Answer: In server/tests/setup.js, we configure an isolated in-memory database store that clears all collections between test cases using afterEach. This prevents test pollution and allows all 16 integration tests to run in under 4 seconds with 100% determinism.

Q10: What is the time complexity of the delta synchronization endpoint?

Answer: The query Note.find({ updatedAt: { $gt: lastSyncedAt } }) runs in $O(\log N + K)$ time, where $N$ is total notes and $K$ is the number of notes updated since that timestamp, thanks to our single-field index on updatedAt.
